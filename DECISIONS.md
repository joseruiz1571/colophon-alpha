## F2 · Card — OSCAL/JSON-Schema draft mismatch discovered while vendoring

- **What was found**: NIST's actual published OSCAL 1.1.2 Assessment Results JSON Schema (`oscal_assessment-results_schema.json`, fetched from the `usnistgov/OSCAL` v1.1.2 GitHub release assets, since the schema is a *build artifact* attached to the release and is not committed to the repository source tree) declares `"$schema": "http://json-schema.org/draft-07/schema#"` and uses draft-07-only idioms (in particular, dozens of definitions use `"$id": "#plain-name-fragment"` as an anchor, which is invalid under JSON Schema 2020-12's stricter `$id` — 2020-12 requires `$anchor` for that purpose and forbids a fragment on `$id`). Relabeling the `$schema` URI to 2020-12 without further rewriting breaks compilation (confirmed empirically: `$id must match pattern "^[^#]*#?$"`).
- **Decision**: vendor NIST's schema byte-for-byte as published (no edits) at `schemas/vendor/oscal_assessment-results_schema-1.1.2.json`, and validate it as the draft-07 document it actually is: `new Ajv()` (draft-07 default) + `ajv-formats`, or equivalently `ajv-cli validate -c ajv-formats -s <schema> -d <doc>` with **no** `--spec` flag. This mirrors how the OSCAL project validates its own generated schemas in its build (`build/Makefile`: `npx ajv compile -c ajv-formats -s .../*_schema.json`).
- **Consequence for §10's probe table**: the literal probe text for C36 (`bunx ajv-cli validate -s schemas/vendor/... -d ... --spec=draft2020`) does not apply to the real NIST artifact — passing `--spec=draft2020` against a draft-07 schema with plain-name-fragment `$id`s fails to compile, regardless of whether the instance document is valid OSCAL. STATUS.md records C36 as done via the draft-07-correct invocation and calls out this discrepancy explicitly rather than silently matching the literal flag or silently failing.
- **Everything we author ourselves** (`schemas/declaration.schema.json`, `schemas/agent-card.schema.json`) is written and validated as JSON Schema 2020-12 per §5, with no such conflict — the mismatch is specific to the third-party NIST artifact.

## F1 · Declare

- **Fail-closed loading**: `loadDeclaration` never throws for a missing file, malformed YAML, or a schema violation — all three surface as `{ valid: false, errors }`. This mirrors the gate's own fail-closed rule (Principle 2) one layer up: nothing downstream should have to distinguish "the Declaration was invalid" from "the Declaration couldn't be read" or "the Declaration wasn't there".
- **`tools[].max_scopes`**: added as an optional field beyond C2's minimum, to give `auth.*` tool grants a place to declare the credential scopes they may request (consumed by the C15 gate rule and by Card `decision_boundaries`).

## F2 · Card

- **OSCAL/JSON-Schema draft mismatch**: see the dedicated section above (added while vendoring the schema, before Card-proper was built).
- **`classification.next_review` default when the Declaration omits it**: the Declaration schema does not require `next_review` (C2's required list), but the Card schema does (C6). `card export` fills a default of today + 60/90/180/365 days for critical/high/medium/low risk tiers respectively when the Declaration doesn't specify one. Both shipped Declarations specify `next_review` explicitly, so this default only matters for future Declarations that omit it.
- **`metadata.id` pattern**: the Card schema requires a UUID *v4* pattern (matching the Declaration schema), not just "any UUID shape". This means C9's "all-zero UUID is invalid" requirement falls directly out of ordinary schema validation — no separate semantic check was needed in `card validate` beyond running the schema.
- **`decision_boundaries[]` derivation**: built deterministically from the Declaration: one `tool_scope` entry per tool grant, one `data_class` entry per unique data class across all tools, one `sandbox_path` entry per write path (or a single "no write paths granted" entry when the sandbox is empty), and one `credential_scope` entry per tool that declares `max_scopes`. This array is documentation for auditors; it is not itself read by the gate's policy, which reads `card.tools[]` directly (see F3).
- **`governance.control_mappings[]`**: populated with a small fixed baseline (NIST AI RMF GOVERN-1.1 / MANAGE-2.3, ISO/IEC 42001 §8.3) describing what having *any* Card with enforced tool/data/sandbox boundaries demonstrates. This is informative metadata on the Card itself, independent of the per-run control evaluation in F7 (`controls/agent-controls.yaml`), which is evaluated against evidence from a specific session, not against the Card in the abstract.
- **`escalation.kill_switch`**: every Card built by `card export` sets `kill_switch.available: true` with a fixed mechanism description (revoke by invalidating the Card file; the gate fails closed on an invalid/missing Card at startup — see F3). A Card with `kill_switch.available: false` only exists as a deliberately crafted lint fixture (`fixtures/cards/high-no-killswitch.card.json`), never as CLI output.
- **`cards/` at the repository root ships pre-exported, committed Cards** for both example Declarations (not just `fixtures/`). This is necessary for §10 probes that reference `cards/<id>.card.json` directly against a fresh clone without first running `card export` (e.g. C22's literal probe text). The demo pipeline (F9) additionally exports its own fresh copies under `out/demo/` on every run, so the committed `cards/` files are a stable, human-reviewable reference copy, not something the pipeline depends on being pre-existing.
- **Card lint (`policy/card.rego`) takes the Card directly as `input`**, not wrapped in an envelope — unlike the gate's `{card, call, context}` input shape (F3), because lint has only one document to reason about.

## F3 · Gate

- **Data classes carry resource scope, not just category**: `data_classes` on a tool grant are opaque, operator-chosen strings — nothing in the schema or policy requires them to be generic categories like `repo_metadata`. The demo Declarations use scoped strings like `branch_protection:colophon-demo-a` so that "may read branch protection for repo A and B" and "may not read it for repo C" are both expressible as ordinary data-class grants, without inventing a separate repo-allowlist construct alongside data_classes. `repo.read_settings` on an out-of-scope repository (C24's third refusal) and a generic data-class violation (C13) are therefore the same policy rule (`GATE-DATA-CLASS-VIOLATION`), which is simpler and, we think, more honest than pretending they're different mechanisms.
- **Where the `data_class` label on a call comes from**: each tool call's `arguments.data_class` names the sensitivity/scope of the specific resource that call targets. For this v1 scripted demo (no LLM driver exists — C23/A4), that label is authored into the scenario YAML by the operator at scenario-design time, not chosen at runtime by an autonomous agent deciding what to claim about itself. A future non-scripted driver would need this derived server-side (e.g. the upstream or gate consulting a resource→data-class registry) rather than trusting caller-supplied metadata; that registry is out of scope for v1. This is recorded here because it is a real simplification, not because it weakens the gate for what v1 actually claims to do: the *decision* of allow/deny given a data-class label is still 100% Rego (Principle 1); only the *labeling* of a specific call's target is input data, as any argument must be.
- **Approval fingerprints are computed once, in TypeScript, not duplicated in Rego**: `input.call.fingerprint` is precomputed by the gate as `sha256(RFC 8785 canonical form of {name, arguments}))` using the same `src/util/canonical.ts` used for Card hashing and the trace chain, and Rego simply reads `input.call.fingerprint` (`policy/gate.rego`, `approval_fingerprint := input.call.fingerprint`). We considered having Rego compute its own hash via `crypto.sha256(json.marshal(...))`, but that risks a silent mismatch against the fingerprint an operator computes when preparing an `--approvals` file (different JSON serialization conventions between Go's `json.marshal` and RFC 8785). Precomputing keeps exactly one canonicalization implementation in the whole system. This does not violate "policy is data, not code" (Principle 1): TypeScript still makes zero allow/deny/escalate decisions; it only computes a value that is, itself, part of the call's data.
- **Single-use approvals are enforced entirely via `context.prior_decisions`**, per C11's input shape — not by the gate mutating or removing entries from the `--approvals` file. Each policy evaluation receives the Card, the call, the full static approvals list, and every decision made earlier in the session; Rego alone decides whether a given approval fingerprint has already been consumed by scanning for an earlier `effect: "allow"` decision carrying that fingerprint. The gate's TypeScript layer only accumulates and forwards `prior_decisions` — it never decides "is this approval still good".
- **Multiple simultaneous violations are all reported together** (`deny_reasons`/`escalate_reasons` are Rego partial sets, unioned into the decision), mirroring `policy/card.rego`'s approach — an operator debugging a denied call should see every rule it broke, not just the first one evaluated.
- **Rule IDs**: `GATE-UNKNOWN-TOOL`, `GATE-DATA-CLASS-VIOLATION`, `GATE-SANDBOX-VIOLATION`, `GATE-SCOPE-EXPANSION`, `GATE-REQUIRES-APPROVAL` (escalate), `GATE-APPROVED` (allow via a consumed approval), `GATE-ALLOWED` (the plain default-allow path). All seven appear in `policy/gate_test.rego`'s 22 tests.
- **`policy/gate.rego` is not usable standalone with `default allow := true` anywhere** — `effect` has no default-allow branch; it is `"deny"` if any deny reason fired, else `"escalate"` if any escalate reason fired, else `"allow"`. Combined with `src/util/opa.ts` treating any OPA process error or undefined query as deny, this is the concrete mechanism behind C18's "never falls open".

## F5 · Trace

- **Credential redaction is key-name-based**, not a manual per-tool allowlist: any argument key matching `/token|secret|password|credential|api[_-]?key/i`, at any nesting depth, is replaced with the literal string `"[REDACTED]"` in `args_redacted` (`src/util/redact.ts`). The separate `args_sha256` field hashes the true, unredacted arguments — an auditor can prove two calls used identical arguments (matching hashes) without the trace ever holding the sensitive value itself (C29).
- **Hash chain genesis**: the first line of a fresh trace file has `prev_hash` equal to 64 zero characters (`GENESIS_HASH`), rather than being null/omitted, so every line — including the first — has a well-formed, fixed-width `prev_hash` to verify.
- **`TraceWriter` resumes an existing file's chain** (reads the last line's `hash` as the starting `prev_hash`) instead of always starting fresh at genesis, so a gate process that appends to the same session across multiple invocations still produces one continuous, verifiable chain.
- **`colophon trace verify` reports 1-indexed line numbers**, matching how a human (or `sed -i '3s/.../.../''`) counts lines, per C28's probe wording ("names the line index").

## F4 · Agent and demo upstream

- **The gate spawns its upstream via `/bin/sh -c "<command>"`**, so `--upstream` can be any shell command string (per SPEC.md's literal `--upstream "<command>"` syntax), not just a bare executable+args. The demo always passes `bun run <abs-path-to-cli> upstream demo`.
- **All upstream tool arguments that name a filesystem path are resolved relative to the repository root**, then checked to still resolve inside `fixtures/` (`src/upstream/fixtures-root.ts`) before any read or write happens — independent of and in addition to the gate's own sandbox check. This is deliberate defense in depth for C21 ("None of them touch the real network or filesystem outside fixtures/"): even a hypothetical gate bug or bypass cannot make the upstream itself touch the real filesystem outside `fixtures/`. `auth.request_scopes`, `net.fetch`, and `mail.send` go further and never perform any real I/O at all — they always return a canned synthetic result.
- **`colophon agent run --list-tools`** (rather than a flag on `gate serve`) is what SPEC.md's C10 probe means by "via the agent's `--list-tools` flag": `agent run` spawns the gate exactly as it would for a real scenario, then calls `tools/list` and exits, without ever calling `tools/call`. `colophon gate serve --list-tools` and `colophon upstream demo --list-tools` also exist as lower-level introspection aliases used directly by a couple of tests, but the CLI usage text advertises the agent-level one since that's what a user actually runs.
- **Scenario file format**: a YAML document with `name`, optional `description`, and `calls: [{name, arguments}, ...]` replayed in file order by `ScriptDriver`. No branching, no conditionals — a scenario is exactly the ordered list of tool calls it names, which is what makes "the agent tried these four things and was refused" a claim a reader can verify by reading the YAML directly.
- **C19 ("changing a single rule in policy/gate.rego flips a decision, zero .ts changes") is verified as an automated test**, not only as a manual one-off: `test/policy-only-control.test.ts` copies `policy/` to a temp directory, textually neutralizes the one sandbox-check line, and asserts the same `{card, call, context}` input that the real policy denies (`GATE-SANDBOX-VIOLATION`) is allowed by the patched copy. The card used is `notifier`'s (which has a real, non-empty sandbox), not `evidence-collector`'s — `evidence-collector` is deliberately read-only end to end (C4's "tools are read-only" requirement) and has no `fs.write` grant to sandbox-check in the first place; a write attempt against it is refused by `GATE-UNKNOWN-TOOL`, not by the sandbox rule, so it cannot exercise C19's specific claim. The evidence-report scenario's own `/tmp/gh-token.json` write (C24) is correctly refused via `GATE-UNKNOWN-TOOL` for exactly the same reason: `evidence-collector` has no write tool to abuse in the first place, which is a stronger refusal than a sandbox check would be.

## F6 · Collect

- **`id` and `sha256` are the same value on every evidence item**, by construction — every collector computes an item's id as `sha256OfCanonical(payload)` and never any other way. `EvidenceStore.add` recomputes the hash on insertion and rejects any item where they disagree (C33); a caller cannot bypass this by handing the store a pre-labeled item with a mismatched id.
- **`MCPTraceCollector` refuses to run at all against a trace that fails `verifyTraceFile`** (throws before producing any items), rather than producing evidence from data it cannot vouch for. This means evidence provenance always implies "the chain was intact when this evidence was pulled from it".
- **`LiveAwsProvider` is a real, gated stub, not a full AWS integration**: its constructor genuinely refuses to build without `AWS_ACCESS_KEY_ID` or `AWS_PROFILE` present (so the gating claim in C32/A3 is real code, not a comment), but its three methods throw a clear "not implemented" error rather than making real AWS API calls, since this build installs no AWS SDK dependency (§3, §5, A4) and no operator credentials were ever supplied to actually exercise one. **This is recorded honestly in STATUS.md as the one deliberate gap in F6**: a live AWS collector "exists behind an interface" exactly as SPEC.md requires, but does not itself perform real AWS calls. Wiring real calls in (almost certainly via `@aws-sdk/client-*`) is the natural next increment.
- **No test, and no other file under `test/`, ever mentions the literal string `LiveAwsProvider` or reads/mentions `AWS_*`** (verified by grep during development, not just asserted) — per anti-claim A3, both are confined entirely to `src/collectors/aws-provider.ts`. This constrained how the F6 test suite could exercise `LiveAwsProvider`'s gating: it deliberately is *not* unit-tested from `test/`, and its constructor behavior is instead documented here and reviewed by hand.
- **Fixture AWS data** (`fixtures/aws/*.json`) is a minimal, synthetic CloudTrail/IAM/S3-encryption trio — just enough shape for `FixtureAwsProvider` to be meaningfully exercised by a test, not a realistic security posture. The `agent-controls.yaml` control set (F7) does not depend on these specific values; they exist to prove the collector interface works, not to back any specific control's evidence in the shipped demo.

## F7 · Report

- **`controls/agent-controls.yaml` is a bare top-level YAML sequence**, not wrapped in a `controls:` key, because SPEC.md's own C34 probe is `grep -c '^- id:' controls/agent-controls.yaml`, which only matches a list item anchored at column 0 — wrapping it in a parent key would indent every entry and break the literal probe for no benefit.
- **Each control's `check` field names a key in `src/report/checks.ts`'s `CHECKS` registry**, a plain TypeScript function, not Rego. SPEC.md's "policy is data, not code" principle (§4) governs *gate* decisions (allow/deny/escalate on a live call) — those, and only those, must come from `policy/gate.rego`. A report control is not a gate decision; it is a read-only, after-the-fact observation over evidence that a gate decision already happened (`effect`, `rule_ids`, Card fields already recorded in the trace/evidence). Encoding "does this evidence satisfy this control" in Rego would not remove any judgment from TypeScript that matters to A1 — A1 is scoped to allow/deny branches on *tool name or argument content* in `src/`, which `src/report/checks.ts` never does (it branches on already-decided `effect` values and Card structure, read after the fact).
- **The 8 required control themes (C35) are covered by exactly 8 controls**, chosen to map one-to-one onto the literal list in C35: `no-outside-calls` (outside), `sandbox-write-boundary` (sandbox), `no-scope-expansion` (scope), `every-deny-has-rule-id` (rule_id), `trace-chain-intact` (chain), `card-not-stale` (stale), `approval-required-enforced` (approval), `bundle-manifest-complete` (manifest). `framework_refs` point at real NIST AI RMF function/category codes and ISO/IEC 42001 clause numbers where a specific one fits; OWASP LLM Top 10 and MITRE ATLAS entries are attached to the two controls most related to excessive agency and credential-scope abuse specifically, since those two frameworks are coarser-grained than the control set.
- **"Evidence UUID" (C36, C37) is read as "evidence id"** — the content-addressed SHA-256 identifier `EvidenceItem.id`/`sha256` defined by C30/C33 — not a separately-minted RFC 4122 UUID. SPEC.md's own evidence-item shape never carries a UUID field, and minting a second identifier per item purely to satisfy the word "UUID" would break evidence's content-addressing (an item's identity is its hash, full stop) for no real gain in traceability. Every observation's `relevant-evidence[].href` is `urn:colophon:evidence:<sha256>`, and `colophon report` verifies every such href resolves in the run's `EvidenceStore` before writing anything (C37; see `src/report/citations.ts`'s `validateCitations`/`MissingEvidenceCitationError`).
- **Checks are evaluated over evidence items, not raw trace lines or the raw Card file** (C34: "a deterministic check the report engine evaluates over evidence"): `src/report/checks.ts`'s `CheckContext` is built entirely from `MCPTraceCollector`'s and `CardCollector`'s output — trace-decision evidence items (payload = one `TraceLine`), the trace summary item, and Card evidence item(s) — so a control's determination is always traceable to specific evidence ids the report cites, never to a side-channel the report doesn't also expose.
- **`colophon report --session <id>` / `--trace <file>` take no `--card` flag** (matches the literal C39 probe), so the Card has to be found, not supplied. `src/report/find-card.ts`'s `findCardBySha256` scans `cards/`, `fixtures/cards/`, and `out/` for a `*.card.json` whose `metadata.canonical_sha256` matches the trace's `card_sha256`. "No match found" is treated the same as "no Card evidence" by every Card-dependent check (`noCardResult` in `checks.ts`) — a conservative failure, not a silent skip, consistent with fail-closed (§4).
- **`bundle-manifest-complete` is an honest, explicitly-labeled proxy**, not a real manifest check: the real bundle (and its `manifest.json`) does not exist yet at `colophon report` time — it is produced by the later `colophon bundle` step (F8). The control instead checks that this run's evidence set is internally consistent (the trace summary's `total_decisions` matches the number of decision evidence items actually collected, and a Card was found) — a proxy for "the eventual bundle's evidence/ directory will be complete", explicitly captioned as such in the control's own `intent` text. `colophon bundle verify` (F8) is the independent, real, file-hash-based check once a bundle exists.
- **`trace-chain-intact` will in practice always evaluate `satisfied` when a report is produced at all**, because `MCPTraceCollector.collect()` (F6) already throws before producing any evidence if `verifyTraceFile` fails — so `colophon report` fails closed on a broken chain *before* any control runs, never by reporting that one control as failed. The control is kept anyway because it makes an implicit fail-closed gate into an explicit, auditable line in `assessment-results.json` and `narrative.md` — an auditor reading the report sees "chain integrity: checked" as a first-class finding, not an assumption baked silently into the tooling.
- **C39's `fixtures/traces/breach.jsonl` is a genuinely hash-chained trace, not a hand-tampered file.** It was generated with the real `TraceWriter` (so `colophon trace verify` on it passes cleanly) and deliberately records one `mail.send` call — a tool `evidence-collector`'s Card does not grant at all — with `effect: "allow"`, simulating a gate defect or bypass that let an out-of-scope call execute. This isolates exactly one thing: `no-outside-calls` should catch an execution that got past the gate by *any* means, purely from trace+Card evidence, and it must not be confused with `trace-chain-intact` (a tampered-bytes concern) or `every-deny-has-rule-id` (a different failure mode entirely) — the fixture leaves those other 7 controls satisfied on purpose.
- **C36's literal probe (`bunx ajv-cli validate ... --spec=draft2020`) cannot succeed against the real vendored OSCAL schema**, for the same reason already recorded above (OSCAL/JSON-Schema draft mismatch): forcing `ajv-cli` into 2020-12 mode makes it look for a draft-07 meta-schema it never loaded, so it fails to even *compile* the schema (`error: no schema with key or ref "http://json-schema.org/draft-07/schema#"`) — this is unrelated to whether the produced document is valid. `colophon report` itself validates every document it writes with `validateAgainstDraft07Schema` (plain Ajv + ajv-formats, matching OSCAL's own build tooling) and fails closed (throws `ReportBuildError`, writes nothing) if that fails; the equivalent working CLI invocation is `ajv validate -s schemas/vendor/oscal_assessment-results_schema-1.1.2.json -d <file> --spec=draft7 -c ajv-formats`, confirmed to pass against `colophon report`'s real output. STATUS.md marks C36 `partial` for this reason: the document is genuinely schema-valid and the engine fails closed on any document that isn't, but the exact probe command as written in SPEC.md §10 cannot pass against this real, correctly-vendored artifact.

## F8 · Bundle and sign

- **`colophon bundle` calls the same `buildReport` engine `colophon report` uses**, rather than expecting a separate `colophon report` invocation to have already populated the bundle directory. This is forced by C40's own wording — bundle "refuses a non-empty output directory" — so the directory bundle writes into must be empty when bundle starts; if a prior `colophon report --out <that dir>/report` had already written into it, bundle's own refusal would fire on a directory *it* is supposed to populate. `colophon report` remains independently useful (and is what SPEC.md's C36/C38/C39 probes exercise directly, against their own scratch `--out` directories), but the demo's own `out/demo/<run>/` bundle directories are populated by `colophon bundle` alone.
- **Evidence, not the OSCAL document, is the thing chunked into individual files.** `evidence/<id>.json` holds one full `EvidenceItem` (`id`, `source`, `retrieved_at`, `sha256`, `payload`) per file — matching C40's "for every item retrieved (cited or not)" literally, including decisions the report's controls never cited. `report/assessment-results.json` and `report/narrative.md` stay single files, matching how `colophon report` already produces them.
- **`manifest.json` hashes raw file bytes, not canonical JSON**, unlike almost everything else in this codebase (Cards, trace lines, evidence items). Most bundle files aren't JSON logically meant to canonicalize (`narrative.md`, the raw `.jsonl` trace copy); hashing bytes is also the only definition of "detect any single byte change" that makes sense for non-JSON files, and it's simpler to apply one rule to every file in the bundle rather than special-case by extension.
- **`root_hash` is `sha256(canonical({files list}))`**, computed from the manifest's own `files` array (path/sha256/size triples) rather than, say, a hash-of-hashes computed some other way — this reuses the same canonicalization primitive as everything else and gives `bundle verify` a second, independent check beyond re-hashing each file individually: if an attacker edits both a file and its manifest entry to match, but doesn't also recompute `root_hash` to match the doctored `files` array, verification still fails.
- **`colophon bundle verify` allow-lists exactly two filenames as expected "extras" not in the manifest: `manifest.json` itself and `manifest.json.sig`** — both necessarily postdate the manifest's own contents (the manifest can't describe its own hash, and its signature can only be computed after it exists), so neither can appear as a manifest-listed file. Any other file present in the bundle directory but absent from `manifest.json` is treated as tampering (an added file), matching C41's "or any added ... file" wording.
- **Cosign v3's default signing config makes even key-pair `sign-blob` contact a public Sigstore instance** (Fulcio, Rekor, a TSA) and upload a transparency-log entry — confirmed empirically: a plain `cosign sign-blob --key ... --bundle ...` against this repo's cosign (`v3.1.3`) embeds a real `tlogEntries` block with a live Rekor log index, which needs the network and is incompatible with `bun test`/the demo/CI all running network-free (§5). **`fixtures/cosign/offline-signing-config.json`** is a Sigstore `SigningConfig` document (schema: `application/vnd.dev.sigstore.signingconfig.v0.2+json`) with every service URL list emptied out; passed via `cosign sign-blob --signing-config <that file>`, it makes both `sign-blob` and `verify-blob --insecure-ignore-tlog=true` fully local — confirmed by running the whole sign→verify→tamper→reject cycle with network access removed from the shell. `src/bundle/sign.ts` always passes this file for the key-pair flow (`colophon bundle sign`/`colophon bundle verify --pub`); the CI workflow's separate *keyless* sign+verify step (F9, C42) is deliberately not routed through this file — keyless signing only exists via GitHub OIDC + Fulcio + Rekor, all of which need the network, and exercising exactly that is what C42 asks the CI step to do. That CI step is the one specific, intentional exception to §5's "no network access" rule, scoped to itself.
- **`Bun.spawn` does not inherit the parent process's environment unless `env` is passed explicitly** — confirmed by reproduction (an unset `env` option made `cosign generate-key-pair` unable to see `COSIGN_PASSWORD` and fall into an interactive prompt, which then fails non-interactively with an "inappropriate ioctl for device" error rather than silently succeeding or failing clearly). `src/bundle/sign.ts` always passes `env: process.env` explicitly to every `cosign` invocation for this reason, and also sets `stdin: "ignore"` so cosign never mistakes an inherited terminal for an interactive session.
- **`colophon bundle sign`/`verify` shell out to the real `cosign` binary via `Bun.spawn`** rather than reimplementing Sigstore's bundle format or ECDSA signing in TypeScript — SPEC.md §5 says the CLI wraps Cosign, not that it reimplements it, and shelling out is the only way to stay compatible with the real `cosign verify-blob` a downstream consumer would run against a shipped bundle.

## F9 · Demo, docs, CI

- **`colophon bundle` already performs collect+report (F8), so `bun run demo` never calls `colophon report` as a separate step** — `src/demo/run.ts` runs declare → card → a gate `--list-tools` smoke check → agent (all three scenarios) → `colophon bundle` (which collects, reports, and assembles) → `colophon bundle verify` → `colophon bundle sign`/`verify --pub`, per scenario. This keeps the demo's `out/demo/<runId>/<scenario>/` directories exactly the shape C40's probe expects (`report/`, `evidence/`, `trace/`, `manifest.json` as direct children), and CI's own "colophon bundle verify" and "schema validation" steps read those same paths.
- **The demo orchestrates the pipeline by calling library functions directly (`runAgent`, `buildBundle`, `verifyBundle`, `signBundle`) rather than shelling out to the `colophon` CLI N times** — each `colophon` invocation still starts a fresh Bun process (and the gate itself spawns a second one for the upstream), so calling in-process where possible keeps the whole demo around 15 seconds, comfortably under C43's 60-second budget, without changing what's actually exercised (the gate and upstream are still real, separate MCP server processes over stdio for every scenario).
- **Card export during the demo writes into `out/demo/<runId>/cards/`, never into the repository's own tracked `cards/`** — the demo must write nothing outside `out/`/`trace/` (A5), so it cannot touch the committed Cards even though `colophon card export`'s normal usage (and this repo's own `cards/*.card.json`) writes there. `colophon report`/`bundle`'s own `findCardBySha256` (F7) still finds the freshly-exported demo Cards because it also scans under `out/`.
- **Each demo run gets a fresh `runId` (a timestamp plus 8 hex characters) and a fresh Cosign key pair under `out/demo/<runId>/keys/`**, so two consecutive `bun run demo` invocations never collide (C44) — confirmed by running it twice in a row, both from a working tree and from a genuinely fresh `git clone`. The demo's own `COSIGN_PASSWORD` is a throwaway value scoped to the run and restored to its previous value (if any) before returning, so it never leaks into whatever else the calling process does afterward. Session ids for the three scenarios are also freshly generated per run (via `runAgent`'s default), so `trace/` only ever grows — consistent with A5's "nothing outside `out/`/`trace/`" allowing `trace/` to accumulate across runs.
- **Verified the whole demo needs zero network access** by running it with `HTTPS_PROXY`/`HTTP_PROXY` deliberately pointed at an unreachable address (`http://127.0.0.1:1`) and confirming it still completes successfully in the same ~15 seconds — this is on top of (not instead of) CI's own network-blocking step below.
- **C19 was verified against the real repository files**, not just the standing `test/policy-only-control.test.ts` unit test: `policy/gate.rego`'s `unknown_tool` rule was patched in place (one added line: `input.call.name != "fs.write"`, meaning "treat fs.write as always-granted regardless of what the Card says"), `scenarios/evidence-report.yaml` was rerun against evidence-collector's Card, and the resulting trace line for the `/tmp/gh-token.json` write shows `"effect":"allow","rule_ids":["GATE-ALLOWED"]` — confirming the *gate's decision* flips purely from the one-line policy edit. `git diff --stat -- src/` was empty throughout, and the patch was reverted (confirmed via `git diff --stat` showing nothing) before committing anything else. One nuance worth recording: the CLI's own step-by-step output still prints that call as "denied", because the synthetic demo upstream (`src/upstream/tools.ts`) independently refuses to touch any path outside `fixtures/` as a defense-in-depth measure *unrelated to the gate's policy decision* (SPEC.md §3: the demo upstream must never touch the real filesystem outside `fixtures/`) — the trace, which is what C19 actually asks about, shows the true post-patch decision.
- **`colophon declare validate`/`colophon card validate` are what CI's "schema validation of all shipped Declarations and Cards" step reuses**, rather than a separate `ajv-cli` invocation — they already wrap the exact schemas (`schemas/declaration.schema.json`, `schemas/agent-card.schema.json`) this claim is about, and reusing them means this CI step is exercising the same code path the rest of the product depends on, not a parallel one that could silently drift from it.
- **CI's offline "bun run demo" step uses `iptables` to actually cut outbound network** (accept loopback, reject everything else, run the demo, then flush the rule before the later Cosign-keyless step needs the network again) rather than only asserting "the demo doesn't call the network" by code inspection. This was tested locally first via a poisoned-proxy run (see above) before committing to the stronger, real network cut in CI.
- **OPA, Cosign, and gitleaks are all installed in CI from their own GitHub Releases directly** (pinned versions: OPA v1.4.2, gitleaks v8.21.2; Cosign via the official `sigstore/cosign-installer` action) rather than through third-party marketplace actions for OPA/gitleaks specifically — this matches how this repository's own dev environment was set up (binaries downloaded directly, recorded in the "General" section above) and avoids a dependency on marketplace-action maintenance for two of the three external tools.
- **CI's "keyless Cosign sign and verify" step could not be exercised locally at all** — `cosign sign-blob` with no `--key` starts an interactive OAuth2 device-code flow that has no non-interactive fallback outside a real OIDC environment (confirmed by reproduction: it hangs waiting for a browser login rather than erroring). This step depends entirely on GitHub Actions' ambient OIDC token (via the workflow's `id-token: write` permission) and can only be verified by an actual CI run on GitHub, not by anything runnable in this build environment — recorded honestly in STATUS.md against C42/C46 rather than claimed as independently tested.
- **The real CI run surfaced two bugs that no amount of local testing could have caught, since both are properties of the hosted GitHub Actions environment itself, not of this repository's code:**
  1. **`sigstore/cosign-installer@v3`'s floating major-version tag resolves to a stale commit that cannot install any cosign v3.x release at all.** Its `action.yml` bootstraps from cosign v2.5.2 and verifies a requested release only via an old-style detached `<file>.sig` asset; every real cosign v3.x release (confirmed against v3.1.1's actual asset list on github.com/sigstore/cosign/releases) ships signatures exclusively as `<file>.sigstore.json` keyless bundles and publishes no `.sig` files at all. First CI run (no `cosign-release` override) silently installed v2.5.2 and failed at `bun test` with `cosign: unrecognized flag: --signing-config` (v2.x predates that flag). Pinning `cosign-release: "v3.1.3"` next failed the installer step itself in ~10s with curl exit 22, because that exact version string isn't a real sigstore/cosign release (this repo's dev-environment cosign binary reports `v3.1.3` via `cosign version` but is evidently a non-public build). Correcting to the real `cosign-release: "v3.1.1"` failed the same way, which is what exposed the actual bug: the *installer action itself*, not the requested version string, was the problem — `@v3` still tried to fetch `cosign-linux-amd64.sig` for v3.1.1, which returns 404, because `@v3` predates cosign's move to `.sigstore.json`. Fixed by pinning the installer action to `sigstore/cosign-installer@v4.1.2` (a real, current release, confirmed to carry full `.sigstore.json` verification logic and to bootstrap from cosign v3.0.6, which itself ships `.sigstore.json` — no chicken-and-egg problem), while keeping `cosign-release: "v3.1.1"` for the actual binary used everywhere else in the workflow.
  2. **CI's "secret scan" step (`gitleaks detect --no-git -v --source .`) flagged the demo's own generated Cosign private key** (`out/demo/<runId>/keys/cosign.key`) as a `private-key` finding once the pipeline finally ran end to end. This is a real password-protected Sigstore private key — `bun run demo` generates a fresh keypair every run precisely so it can demonstrate real signing — not a leaked credential: it's gitignored, encrypted under a per-run throwaway `COSIGN_PASSWORD`, and lives beside, not inside, the trace/evidence/report/bundle artifacts A2 actually requires to be credential-free. Reproduced locally (`bun run demo` then `gitleaks detect --no-git -v --source .` → one `private-key` finding at exactly that path) before deciding on a fix, to confirm it wasn't CI-environment-specific. Fixed with a `.gitleaks.toml` that extends gitleaks' default rules (`[extend] useDefault = true`, so nothing is weakened) and adds a narrowly-scoped `[allowlist]` on `out/demo/[^/]+/keys/.*` only — every other path, including the trace/evidence/report/bundle files the demo itself produces and all committed source, is still scanned; confirmed locally this reduces the same post-demo scan to "no leaks found". Considered and rejected running the secret scan before `bun run demo` instead: A2's claim explicitly covers "trace, evidence item, report, or bundle" — artifacts that don't exist until after the demo runs — so scanning before it would silently stop testing the actual claim.
